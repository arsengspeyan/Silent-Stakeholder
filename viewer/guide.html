Slide 1 — Introduction

Silent Stakeholder

A pipeline that reads what users say in app store reviews and what the development team plans on GitHub — then finds the gaps between them.

Every product has users who never get a seat in sprint planning. They leave reviews instead of filing tickets. Those reviews pile up — thousands of them — while the team tracks work in GitHub issues and milestones. Nobody systematically connects the two.

Silent Stakeholder is that bridge. The analysis targets PPSSPP, an open-source PlayStation Portable emulator, chosen for its large review corpus and a real public GitHub roadmap on the same product.

App: PPSSPP · package org.ppsspp.ppsspp

GitHub repo: hrydgard/ppsspp

User data: 9,771 reviews from HuggingFace sealuzh/app_reviews

Roadmap data: 4,004 GitHub issues + 70 milestones

Output: Top 5 latent unmet needs — each with a confidence score, review IDs as evidence, GitHub issue IDs, and a verdict

What makes this different from a summarizer

A summarizer tells you "users complain about lag." This system finds latent needs — patterns across hundreds of reviews where users circle the same underlying problem using completely different words, but never state the need directly.

A system — not a summarizer. It finds patterns users never stated directly, and every gap links to specific review IDs and GitHub issue IDs that are fully traceable.
Slide 2 — The problem

Two groups. One product. Never in sync.

Developers plan features in GitHub. Users express frustration in app store reviews. These two channels almost never talk to each other. The result: teams ship things users don't urgently need, while real pain points stay unbuilt — sometimes for years.

Users are the silent stakeholders — affected by every product decision but with no structured voice in planning. Reviews are the closest thing to that voice at scale, but they are messy, repetitive, and hard to act on without processing.

What this is NOT

  • Not listing the most frequent complaint words
  • Not asking AI to guess the top user needs from scratch
  • Not producing scores the LLM made up
Complaints are easy — anyone can count the word "lag." Latent needs are different: what users needed but never said in one sentence, proven by clustering math across hundreds of reviews.
Slide 3 — Data sources

Same product. Both sides. Traceable IDs.

The pipeline connects one app’s user signals with its public roadmap. The ingest stage pulls both sides and assigns every record a stable ID that never changes between runs. IDs are the evidence currency — each gap points to specific reviews like rev_0142 or issues like #15281.

User signals — reviews

  • Source: HuggingFace sealuzh/app_reviews (288k reviews across all apps)
  • Filtered to PPSSPP only → 9,771 reviews
  • Sorted by date + text before ID assignment → deterministic
  • Each review: rev_0001, text, star rating, date
  • Cached in data/reviews.json

Team roadmap — GitHub

  • Source: GitHub API on hrydgard/ppsspp
  • 9,900 raw records → 4,004 real issues (PRs removed)
  • 70 milestones (open + closed) for priority context
  • Issue ID = GitHub issue number (permanent)
  • Cached in data/issues.json, data/milestones.json

Why PPSSPP specifically

Large review set for an open-source app, active GitHub with real milestones, and genuine tension between what passionate users want (compatibility, performance) and what a small team can deliver. Wikipedia Android was considered first — but its issues live on Phabricator, not GitHub.

Every record has a stable ID. Each gap links to the exact review and the exact GitHub issue — nothing is vague or hand-waved.

Why the LLM is not the brain

Every gap in the output must be traceable and reproducible. If an LLM decides grouping, scores, or rankings, the result becomes an opinion that changes between runs and cannot be explained with a fixed rule. Silent Stakeholder is built so that a confidence score like 81.3% always comes from the same formula applied to the same data — not from a model’s intuition.

What code handles (no LLM)

  • Ingest — download and assign IDs. Pure data work.
  • Cluster — local embeddings + HDBSCAN. Same input always gives the same groups.
  • Match — cosine similarity against 4,004 issues. Verdict rules from issue state and milestones.
  • Score — explicit formula. Ranking is a sort by that number.

Where the LLM is used (and why)

  • Label — turn 20 sample reviews into one plain-language need sentence. Naming only; cluster membership stays fixed.
  • Match (edge case) — when an active GitHub issue exists and similarity is high, the LLM decides between MISUNDERSTOOD and addressed. Cached; rules handle everything else.

Why not use the LLM for clustering?

  • Cost & speed — embedding 9,771 reviews locally takes ~1–2 minutes and costs nothing. An LLM call per review would be slow and expensive.
  • Reproducibility — the same reviews always produce the same vectors and the same clusters. An LLM might group differently each run.
  • Evidence integrity — cluster membership is ground truth for the whole pipeline. The LLM must not move reviews between groups to "fit a narrative."
  • Scale — similarity math handles thousands of reviews at once. LLMs have context limits and cannot reliably compare 9,771 texts to each other in one pass.

Why not use the LLM for confidence scores?

A score like 81.3% vs 57.3% must mean something consistent and explainable. A formula with published weights (35% volume, 20% tightness, 45% gap clarity) lets anyone recalculate the number from the raw inputs. An LLM saying "87% confident" would not be comparable across gaps — and the difference between 90% and 55% would have no fixed meaning.

How to demo

  • make run — runs all 5 stages, produces gaps.json
  • make viewer — copies results and starts a local web server
  • Open http://localhost:8000/viewer/ — no AI runs here, just displays the output
The LLM names clusters and resolves a few ambiguous verdicts — nothing else. Grouping, scores, and rank come from algorithms and a published formula. Any confidence number traces to a specific line in score.py.
Slide 6 — Stages 1 & 2

Ingest + Cluster — finding patterns in noise

Stage 1 · Ingest

Downloads both data sources and normalizes them into JSON files with stable IDs. Uses cache on re-run — only re-fetches with --refresh.

  • Reviews from HuggingFace, filtered to PPSSPP
  • GitHub issues via API (PRs excluded)
  • GitHub milestones for roadmap context
  • Code: src/ingest.py

Stage 2 · Cluster

Groups reviews that talk about similar things — using local math, no API calls. This is where latent patterns are discovered.

  • Embed each review with sentence-transformers (CPU)
  • Drop reviews under 50 chars ("Good", "Nice")
  • UMAP: compress 384 dimensions → 10
  • HDBSCAN: find dense groups automatically
  • Result: 23 clusters + noise
  • Code: src/cluster.py

Why HDBSCAN, not k-means

The pipeline does not require guessing how many needs exist upfront. HDBSCAN finds the count automatically and marks reviews that don't fit any group as noise instead of forcing them into the wrong cluster. That keeps the evidence clean.

Cluster membership is ground truth. The algorithm decides which reviews belong together. The AI only names the group afterward — it never moves reviews between clusters.
Slide 7 — Stages 3, 4 & 5

Label + Match + Score — from groups to ranked gaps

Stage 3 · Label (src/label.py)

Claude reads up to 20 sample reviews from each cluster (longest first — more context) and returns JSON with three fields: need (one sentence, user's perspective), theme (2–4 word label), summary (evidence pattern). Every API call cached to data/label_cache/ — re-runs are free.

Stage 4 · Match (src/match.py)

Embeds each labeled need and all 4,004 issue titles+bodies. Finds top-5 most similar issues via cosine similarity. Then applies rule-based verdicts:

  • Best similarity below 0.35 → IGNORED (roadmap has nothing)
  • Related issue shipped in closed milestone but users still complain → MISUNDERSTOOD
  • Related issues exist but none actively worked on → UNDER-PRIORITIZED
  • Active open issue exists → LLM decides MISUNDERSTOOD vs addressed (cached)

Stage 5 · Score (src/score.py)

Runs the confidence formula on every gap candidate. Merges clusters that represent the same underlying need (documented in code with reasons). Ranks all gaps, picks top 5 as headline findings. Writes gaps.json with full evidence traces and formula breakdown per gap.

Every LLM call is hashed and cached to disk. Stages 1–4 can re-run without cost. The final ranking and every confidence percentage come entirely from the formula in score.py.
Slide 8 — Confidence formula

Every percentage comes from code — not AI opinion

Each gap gets a confidence score from an explicit formula with three inputs. Weights are constants at the top of score.py — change them and re-run in seconds. The full calculation string is stored in every gap record and shown on the Results page.

confidence = (0.35 × volume) + (0.20 × tightness) + (0.45 × gap_clarity)
Gap clarity 45% Volume 35% Tightness 20%

Volume (35%)

How many reviews support this need? Log-scaled so 500 reviews doesn't get 10× the weight of 50 — diminishing returns for very large clusters.

Tightness (20%)

Mean cosine similarity within the cluster. High = reviews say similar things. Low = varied wording (still valid, but weaker evidence).

Gap clarity (45%) — the most important signal

How clearly does the roadmap miss this need? IGNORED = 1.0 · UNDER-PRIORITIZED = 0.8 · MISUNDERSTOOD = 0.6. Gets the highest weight because a loud complaint the team is already fixing is less urgent than one they've ignored entirely.

Gap #1 worked example — 81.3%

(0.35 × 0.9991) + (0.20 × 0.5189) + (0.45 × 0.80) = 0.8135 → 81.3%

513 reviews (merged from 3 clusters) · tightness 0.52 · UNDER-PRIORITIZED · GitHub issues exist but not actively prioritized

Every confidence score is produced by the same formula in score.py. The breakdown is stored in gaps.json and shown on the Results page — 81.3% is arithmetic on volume, tightness, and gap clarity, not a guess.
Slide 9 — Verdicts

Three verdicts — what the roadmap is doing wrong

Every gap gets exactly one verdict comparing the user need against the closest GitHub issues. Verdicts are assigned by rules in match.py, using issue state, milestone status, staleness, and similarity score.

Ignored

No GitHub issue is similar enough (similarity < 0.35). The team may not know this need exists at all.

Under-prioritized

Related issues exist but are closed, stale (not updated in 2+ years), or not assigned to an open milestone. Acknowledged but not being worked on.

Misunderstood

The team is working on something related — but from the wrong angle. Or they shipped a fix and users still report the same problem.

Real example — Black screen rendering (rank #10, 63.9%, MISUNDERSTOOD)

Issue #15469 "Black screen on Raspberry Pi 3B" was closed and shipped in milestone v1.14.0. The team considers it fixed. But Android users are still reporting black screens in reviews. The team fixed a Pi-specific edge case — not the general rendering failure users experience on their phones.

This is the clearest MISUNDERSTOOD case: the roadmap thinks the problem is solved. Users disagree.

MISUNDERSTOOD is often the most valuable finding — it reveals where the team and users are talking past each other, even when both sides are actively engaged.

Slide 11 — Summary & demo

What Silent Stakeholder delivers

The output

A ranked list of unmet user needs — each with a plain-language description, a formula-based confidence score, hundreds of review IDs as evidence, matched GitHub issue IDs, and a verdict showing how the roadmap relates to that need.

Three design principles

  • Latent, not literal — finds patterns users never stated directly, using clustering math across thousands of reviews
  • Evidence-first — every gap links to specific rev_XXXX IDs and GitHub issue numbers; nothing is hand-waved
  • Code decides, AI assists — grouping, scoring, and ranking come from algorithms and a published formula; the LLM only names clusters and handles edge-case verdicts

PPSSPP — headline finding

The top gap: games run poorly (performance & compatibility) — 81.3% confidence, 513 reviews, UNDER-PRIORITIZED. Three clusters merged. GitHub has related issues but none are actively prioritized in an open milestone.

Why this matters

Open-source maintainers and product teams get a structured, ranked view of what users actually need — compared directly against what the team has planned — without reading thousands of reviews manually or trusting an AI summary.

Silent Stakeholder turns thousands of individual review voices into a small set of evidence-backed gaps — and holds them up against the roadmap to show what is missing.
